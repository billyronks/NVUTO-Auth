# Architecture and threat model

The new service owns only auth_* tables. There are no product profile joins, external monorepo imports, runtime demo hooks, Redis dependency, JWT signing or hidden shared middleware. A deployment represents one product/workspace. The database schema retains tenant IDs and all tenant-sensitive queries use authoritative account state; adversarial extra tenants are exercised in acceptance tests.

Opaque access/refresh credentials and email/MFA/step-up grants use 32 random bytes and SHA-256 storage hashes. Passwords use bcrypt cost 12. Recovery codes are high-entropy opaque values, not human-selected passwords. MFA seeds and undelivered email bodies use AES-256-GCM, random nonces and explicit key IDs authenticated as associated data. Old keys must remain available until rotation and backup verification complete. No default or JWT-derived encryption key exists.

A database transaction locks the user before consuming or rotating grants/sessions. Credential changes increment version, revoke sessions and delete grants and pending enrollment. Refresh tombstones remain with the session; reuse revokes its whole family. MFA challenges are short-lived, version-bound, limited to five attempts and single-use. The user lock and conditional recovery-code deletion provide one consuming transition. TOTP tracks the last accepted time step.

Sensitive operations require a recent, single-use step-up grant bound to the same user, version and session. MFA users must prove both the current password and a factor. Active MFA survives abandoned setup. New enrollment has a separate encrypted secret, opaque identifier, version, expiry and attempt budget. Confirmation swaps it and replaces recovery codes in one transaction. An administrative MFA reset requires a current owner and proof, cannot target self or another tenant, and leaves the target restricted to re-enrollment.

All protected calls resolve the opaque access hash through a current live session, current user version, verified active identity and active tenant. Revocation and suspension therefore affect newly authorized calls immediately. Already-running requests may finish if their read linearized before revocation; credential mutations recheck inside the shared identity lock. No authorization claims come from browser headers other than the bearer credential.

Owner/member are the only identity roles. The product defines and enforces resource permissions. Custom-role mutation, elevated public signup, owner transfer and central identity-provider functionality are outside v0.1.0. A private local bootstrap is the only owner-creation flow.

Threats addressed: credential-purpose confusion, MFA bypass, grant replay, session resurrection, concurrent refresh/recovery races, stale memberships, cross-tenant email collisions, ordinary-session factor replacement, browser ambient-cookie authority, predictable encryption keys, accidental product data disclosure, partial credential commits and secret-bearing diagnostics. Database compromise, application-host compromise, malicious extensions/XSS in a consuming application, mailbox compromise and operator key loss require deployment and incident controls beyond these guarantees.

The runtime database role has no schema/migration authority, no audit modification/deletion privileges and no auth-schema mutation privileges. Maintenance uses the migration role offline. Audit events commit with sensitive changes, contain IDs and event names, and have a default 180-day retention. Failed-authentication request volume is observable through auth_rate; central log/metrics aggregation and alert routing are deployment responsibilities. Request bodies and credentials are never logged.
